# 아이템과 장착 무기

코스튬은 회원 단위로 보유하고, 아이템은 캐릭터 단위로 보유한다. 현재 장착을 지원하는 슬롯은 무기(`WEAPON`)와 모자(`HAT`)다. 관리자 목록·등록·수정·PNG 업로드를 지원한다. 숲 화면에서 인벤토리·장비 선택 UI를 지원한다. 거래·강화는 아직 구현하지 않았다. V16부터 전투와 몬스터 드롭 보상을 지원한다. 장비 능력치 저장과 캐릭터 능력치 합산을 지원한다.

## 관리자 아이템 관리

- `/items` 목록에서 이름·아이템 코드 검색, 종류·상태 필터와 20개 단위 페이지 이동을 지원한다. 활성 `ADMIN`, `SUPER_ADMIN`이 사용할 수 있다.
- 종류는 기타(`MATERIAL`), 소비(`CONSUMABLE`), 무기(`WEAPON`), 모자(`HAT`)를 제공한다. 기존 DB의 방어구 종류는 향후 확장용으로 남겨두며 등록 화면에는 노출하지 않는다.
- `/items/new`에서 이름·고유 코드·종류·설명·상태와 선택적 PNG 이미지를 등록한다. 이름은 100자, 설명은 2000자 이내다. 코드는 소문자·숫자로 시작하는 소문자·숫자·밑줄·하이픈 1~64자로 정규화한다.
- `/items/{id}`에서 이름·설명·상태와 이미지를 수정한다. 기존 보유·장착 참조를 유지하기 위해 고유 코드와 종류는 등록 후 변경하지 않는다. 기본 무기 `wooden-club`은 새 캐릭터 생성에 필요하므로 사용 중 상태를 유지한다.
- 이미지는 애니메이션이나 별도 아이콘 없이 아이템당 PNG 한 장이다. 기타·소비·모자는 정확히 32×32, 무기는 가로·세로 각각 1~512 픽셀을 허용한다. 최대 5MB이며 서버에서 PNG 시그니처·크기·디코딩을 확인한다. 원본 크기와 바이트를 유지한다.
- Flyway V10이 `gm_item.image_key`를 추가한다. 코스튬과 같은 스토리지 설정을 사용하며 `items/{itemId}/{imageId}.png`에 저장한다. 업로드 실패 시 기존 키를 유지하고 DB 롤백 시 새 업로드를 삭제한다. 교체 전 이미지는 자동 삭제하지 않는다.
- 게임의 인증된 `GET /api/items/{itemId}/image`는 DB 키에 해당하는 공개 버킷 PNG를 전달한다. 업로드 전의 기존 무기는 로컬 `weapons/{appearanceCode}.png`로 대체한다. 캐릭터 선택창·게임·장착 표시 모두 해당 API를 사용한다.

## 테이블

`V7__gm_item_weapon.sql`에서 다음 테이블을 만든다.

| 테이블 | 역할 |
|---|---|
| `gm_item` | 아이템 정의: 고유 코드, 이름, 설명, 종류, 장착 슬롯, 외형 코드, 관리 상태, 등록·수정 일자 |
| `gm_character_item` | 실제 보유 아이템: UUID, 캐릭터, 아이템 정의, 수량, 획득·수정 일자 |
| `gm_character_equipment` | 슬롯별 장착: 캐릭터, 슬롯 코드, 보유 아이템 UUID, 등록·수정 일자 |

아이템 종류는 `WEAPON`, `HAT`, `ARMOR`, `CONSUMABLE`, `MATERIAL`, 관리 상태는 `DRAFT`, `ACT`, `INACTIVE`다. 장착 무기는 보유 행마다 수량 1로 저장한다. 같은 종류의 무기라도 보유 UUID가 달라 향후 개별 강화 수치를 추가할 수 있다. 비장착 아이템의 수량도 저장할 수 있으나 겹치기 한도는 아직 정의하지 않았다. V19부터 소비 아이템의 고정 HP 회복 효과를 지원한다.

슬롯별 고유 제약으로 같은 캐릭터의 한 슬롯에는 하나만 장착할 수 있다. 보유 UUID 고유 제약으로 한 아이템을 중복 장착할 수 없다. 캐릭터·보유 UUID 복합 외래키로 다른 캐릭터의 보유 아이템 참조를 막는다. 장착 API는 추가로 로그인 회원의 캐릭터인지, 해당 캐릭터의 수량 1인 사용 중 무기인지 확인한다.

캐릭터 삭제 시 닉네임과 소유자를 확인하고 캐릭터 행을 잠근 뒤 장착 정보 → 보유 아이템 → 캐릭터 순서로 명시적으로 삭제한다. 회원 공유 코스튬과 아이템 정의는 유지한다. 장착·해제도 같은 캐릭터 행을 잠가 동시 요청을 직렬화한다. FK 참조 동작 옵션은 사용하지 않는다.

## 기본 몽둥이

- 아이템 코드와 외형 코드: `wooden-club`
- 최초 아이템 UUID: `20000000-0000-4000-8000-000000000001`
- 이름: `몽둥이`, 종류·슬롯: `WEAPON`, 상태: `ACT`
- 이미지: `local-assets/weapons/wooden-club.png`
- HTTP 경로: `/asset-files/weapons/wooden-club.png`
- 원본은 새로 제공된 64×64 투명 PNG로 교체했다. 로컬 파일과 번들 대체 이미지 모두 `wooden-club.png` 파일명을 유지하며, 게임에서는 64×64로 표시한다. 선택창은 데스크톱 64×64, 모바일 48×48로 표시한다.

마이그레이션은 기존 캐릭터마다 몽둥이 1개를 지급·장착한다. 새 캐릭터도 생성 트랜잭션에서 코스튬 지급·캐릭터 저장·몽둥이 지급·장착을 함께 처리한다. 기본 무기 정의가 없거나 비활성 상태여서 지급하지 못하면 생성 전체를 롤백한다. 기본 정의는 외형 코드가 아닌 고유 `item_code`로 조회하므로 나중에 외형 이미지를 바꿀 수 있다.

기본 정의 INSERT문은 [default_weapon.sql](../sql/default_weapon.sql)에 있다. Flyway V7이 자동 등록하므로 별도로 실행할 필요는 없다. 관리자 아이템 목록은 같은 `gm_item` 행을 조회한다. 업로드 전에는 설정된 에셋 폴더의 `weapons/{appearanceCode}.png`를 사용하고, 관리자에서 이미지를 업로드하면 스토리지 이미지를 우선 사용한다.

## API

- `GET /api/characters/{characterId}/items`: 본인 캐릭터의 보유 목록. `characterItemId`, `itemId`, `itemCode`, `name`, `itemType`, `quantity`, `appearanceCode`, `equipped`를 반환한다. 본인 캐릭터가 아니면 빈 목록이다.
- `PUT /api/characters/{characterId}/weapon`: `{ "characterItemId": "UUID" }`로 장착한다. 반드시 아이템 정의 UUID가 아닌 보유 UUID를 보낸다. `null`이면 장착만 해제하고 보유 행은 유지한다. 본인 캐릭터가 아니면 404, 장착 불가능한 아이템은 400이다.
- `GET /api/characters`와 생성 응답에는 `weapon`이 추가된다. 장착 시 `{ characterItemId, itemId, itemCode, name, appearanceCode }`, 미장착 시 `null`이다.

모든 API는 로그인 세션을 확인하고 캐시하지 않는다. 변경 요청은 CSRF 헤더가 필요하다. 변경 후 목록을 다시 조회하면 선택창에도 해당 무기 또는 미장착 상태가 반영된다. 임의 아이템 지급 API는 노출하지 않는다.

선택창의 무기는 기존처럼 캐릭터 옆에서 수직으로 부유한다. 게임에서는 무기의 손잡이 기준점을 캐릭터 손 근처에 붙여 들고, Z 공격은 손잡이를 축으로 뒤로 당기기 → 전방 스윙 → 복귀 순서로 재생한다. 장착하지 않았거나 잘못된 외형 코드이면 표시하지 않는다. 기본 몽둥이 이미지 누락은 번들 이미지로 대체하고 다른 무기의 이미지 누락은 숨긴다. 선택창의 걷기 모션과 무기 부유 모션은 동작 줄이기 설정에서 정지한다. 게임에서는 무기가 걷기·점프와 손 위치를 따라가며 대기 중에는 부유하지 않는다. 게임에서 Z로 장착 무기를 휘두를 수 있다. 장비·인벤토리 UI는 [숲 탐험](game.md)의 창에서 제공한다. 몬스터 명중·피해 판정과 처치 보상은 [몬스터 전투와 성장](battle.md)을 참고한다.

## 무기 착용 레벨 제한

Flyway V12에서 `gm_item.required_level` INTEGER NOT NULL DEFAULT 1을 추가한다. 모든 기존 아이템은 1로 초기화한다. 무기는 1 이상의 착용 최소 레벨을 설정하고 기타·소비·방어구는 1로 유지한다. 정의 가능한 최고 레벨과는 FK로 연결하지 않아 향후 레벨용 무기도 미리 등록할 수 있다.

관리자 아이템 등록·상세에서 종류가 무기이면 착용 레벨 제한을 입력하며 목록에도 표시한다. 새 캐릭터에게 지급하는 `wooden-club`은 1레벨로 고정하고 서버와 DB가 변경을 막는다. 장착 API는 캐릭터 행을 잠근 뒤 보유·종류·수량·관리 상태와 함께 `required_level <= 캐릭터.level`을 검사한다. 조건 미달은 HTTP 400이고 기존 장착은 변경하지 않는다. 무기 해제는 레벨에 관계없이 가능하다.

인벤토리 응답에는 `requiredLevel`을 포함한다. 관리자가 이미 장착한 무기의 제한을 올려 현재 레벨이 부족해지면 다음 조회부터 캐릭터 응답의 무기는 NULL, 인벤토리의 equipped는 false로 반환한다. 보유·장착 저장 행을 삭제하지 않으며 해당 레벨을 충족하면 다시 표시된다. 아이템 이미지 조회에는 착용 레벨 제한을 적용하지 않는다.

`ItemLevelPostgresTests`는 V12까지 적용한 별도 로컬 `weapon_level_test` DB에서만 실행하며 `ITEM_LEVEL_TEST_URL`이 없으면 건너뛴다.

## 모자와 장비 능력치 (V13)

Flyway V13은 종류·슬롯 `HAT`를 추가하고 무기·모자에 동일하게 착용 최소 레벨을 허용한다. `gm_item.attack`, `defense`, `hp`는 장착 시 추가하는 공격력·방어력·최대 체력이며 0 이상의 INTEGER, 기본값 0이다. 기존 장비의 추가 능력치는 모두 0으로 시작한다. 기타·소비 및 예약된 ARMOR 종류는 추가 능력치 0, 착용 레벨 1을 유지한다. 기본 몽둥이도 추가 능력치는 수정할 수 있다.

관리자 등록·상세는 무기 또는 모자를 선택했을 때 착용 레벨·공격력·방어력·체력을 표시하고 저장한다. 목록과 종류 필터에 모자를 포함하고 각 능력치를 표시한다. 모자 이미지는 현재 32×32 PNG 한 장(최대 5MB)으로 등록한다.

`PUT /api/characters/{characterId}/hat`은 무기 API와 동일한 `{ "characterItemId": "보유 UUID" }`로 모자를 장착하고 null이면 해당 슬롯만 해제한다. 로그인·CSRF·캐릭터 소유·보유 수량 1·HAT 종류·HAT 슬롯·ACT 상태·최소 레벨을 검증한다. 무기와 모자는 각각 한 개씩 장착한다. 무기 API로 모자를 장착하거나 모자 API로 무기를 장착할 수 없다.

캐릭터 응답의 maxHp·attack·defense는 레벨별 기본 수치 + 유효하게 장착한 무기·모자의 추가 수치 합계다. 사용 중지, 수량 오류, 슬롯 불일치 또는 레벨 미달 장비는 합산하지 않는다. 능력치를 영구 복사하지 않으므로 장착·해제·관리자 수정 후 다음 조회에 반영된다. 합계는 BIGINT/Java long으로 계산한다. 신규 캐릭터 생성 응답에도 기본 몽둥이의 추가 수치를 더한다. 인벤토리 응답은 아이템의 attack·defense·hp를 포함한다.

아이템 중 캐릭터 외형에 표시하는 종류는 무기뿐이다. 모자·기타·소비 이미지는 가방·아이템 목록용 이미지이며 캐릭터 위에 표시하지 않는다. 모자는 장착 시 능력치만 반영한다. 가방·장비 선택 UI는 숲 화면에서 제공하며, 전투 피해 판정·현재 체력 저장은 V16에서 지원한다. 실제 PostgreSQL 경계·합산 테스트는 V13까지 적용한 폐기용 DB에서만 실행한다.

## 손에 드는 무기 이미지

게임의 `weaponGrip.ts`는 투명 PNG의 아래쪽 불투명 픽셀에서 손잡이 기준점을 찾고, 위쪽 무기 끝으로 향하는 축을 읽는다. 기존 세로 이미지와 대각선 이미지 모두 지원하며 원본 파일은 변경하지 않는다. 캐릭터 좌우 방향에 따라 무기만 반전하고 같은 손 위치에서 휘두른다. 이미지 종횡비를 유지하고 긴 변을 64px로 맞춘다. 빈 이미지나 픽셀 읽기 실패 시 기존 세로 이미지 기준점을 사용한다.

새 이미지 권장 규격은 64×64 투명 PNG이며, 손잡이는 아래쪽(대각선이면 왼쪽 아래), 타격부는 위쪽(오른쪽 위)에 두는 방식이다. 손잡이 아래에 별도 장식·그림자·다른 물체를 넣지 않아야 기준점이 정확하다. 이미지별 세밀한 손 위치는 실제 등록 이미지를 보고 조정할 수 있다. 관리자 업로드와 서버 API·DB 규격 변경은 없다. 타격 판정은 기존 스윙 시작 후 약 90ms 시점을 유지한다.

## 소비 아이템 HP 회복 (V19)

`gm_item.heal_hp INTEGER NOT NULL DEFAULT 0`은 사용 시 회복할 HP다. 0 이상만 허용하고 소비(`CONSUMABLE`) 이외 종류는 0으로 유지한다. 기존 아이템은 모두 0으로 초기화한다. 장비의 `hp`(추가 최대 체력)와 독립된 값이며 새 테이블은 만들지 않는다.

관리자 아이템 등록·상세에서 종류가 소비이면 HP 회복량을 입력·수정할 수 있다. 목록에도 회복량을 표시한다. 0이면 회복 효과가 없어 사용할 수 없다. 기존 소비 아이템도 상세에서 양수로 설정하면 회복 아이템으로 사용할 수 있다. 게임 백엔드를 먼저 재시작해 V19를 적용한 뒤 관리자 서버를 재시작한다.

인벤토리 API는 `healHp`를 포함한다. 숲 인벤토리에서 회복 아이템을 선택하면 회복량과 `사용하기` 버튼을 표시한다. `POST /api/characters/{characterId}/items/{characterItemId}/consume`은 로그인·CSRF·캐릭터 소유·보유 아이템·소비 종류·ACT 상태·양수 회복량을 확인한다. 응답은 `currentHp`, `maxHp`, 실제 회복한 `healedHp`다.

회복은 유효 장비를 합산한 최대 체력까지만 적용한다. 현재 체력 NULL은 최대 체력으로 처리한다. 체력이 가득 찼거나 쓰러진 상태이면 HTTP 400을 반환하고 소비하지 않는다. 성공 시 `gm_character.current_hp` 갱신과 `gm_character_item.quantity` 1개 차감을 한 트랜잭션에서 처리하며 마지막 1개이면 보유 행을 삭제한다. 캐릭터 행 잠금으로 전투·장비 변경·동시 사용과 직렬화하고, 소비 아이템 정의도 공유 잠금으로 사용 도중 관리자 변경을 방지한다.

`ConsumablePostgresTests`는 `HEALING_TEST_POSTGRES_URL=jdbc:postgresql://127.0.0.1:포트/healing_test`인 전용 폐기용 PostgreSQL에서 실행한다. 계정은 `healing_test` / `healing_test_password`이며 V19까지 적용한다. 최대 체력 제한, 장비 합산, 사용 불가 조건, 마지막 수량 삭제, 전체 롤백, DB 제약과 마지막 1개 동시 사용을 검증한다.

퀵슬롯은 소비 아이템 정의 ID를 등록해 클릭·`Q W E R / A S D F`로 같은 소비 API를 실행한다. 동일 아이템의 여러 보유 행 수량을 합산하고, 소진 후 재구매해도 연결을 유지한다. [게임 조작](game.md)의 퀵슬롯 설명을 참고한다. NPC 상점에서도 기존 소비·장비 아이템을 구매할 수 있으며 [NPC 관리](npcs.md)에 구매 규칙을 정리했다.
